# 12WY Bot — 12 Week Year + Essentialism

Telegram-бот для комьюнити: ведёт участниц по системе 12 Week Year через фильтр Essentialism
(Explore → Eliminate → Execute), с еженедельными чек-инами, скорингом и командами поддержки.

## Mini App (приложение внутри Telegram)

Переезд с чат-онбординга на Mini App идёт экран за экраном (бриф — `docs/miniapp-brief.md`).
Бот и веб-сервер работают **в одном процессе**: aiogram (polling, расписание, бэкап) + FastAPI (API и статика
фронтенда) на порту `PORT` (8080). Адрес приложения — `WEBAPP_URL`, на Fly по умолчанию
`https://<app>.fly.dev`. Telegram открывает Mini App только по HTTPS.

- **Авторизация** — без паролей: фронтенд шлёт `initData` из Telegram WebApp SDK (`Authorization: tma …`),
  бэкенд проверяет подпись HMAC-SHA256 токеном бота и срок (сутки) — `webapp/auth.py`.
- **Фронтенд** — чистые HTML/CSS/JS без сборки (`webapp/static/`), цвета из темы Telegram,
  родные MainButton/BackButton и haptic.
- `/start` показывает кнопку «🌿 Открыть приложение», а кнопка меню слева от поля ввода открывает приложение.
  Пока шаги не переехали, в чате остаётся запасная кнопка и прежний онбординг.

| Экран | Статус |
|---|---|
| Приветствие | ✅ в приложении |
| Колесо баланса (ползунки + радар, сравнение с прошлым циклом) | ✅ в приложении |
| Explore → Eliminate (ровно 3) → Essential intent | ✅ в приложении |
| Тактики с 12-недельным планом (каждую неделю — с днями недели / выбранные недели / одна неделя) | ✅ в приложении |
| Итог и подтверждение → «готова» и команда | ✅ в приложении |
| Главная: неделя N, средний %, график по 12 неделям | ✅ в приложении |
| Чек-ин недели (✓/✕ по тактикам этой недели) и результат | ✅ в приложении (и по-прежнему в чате) |
| Экран команды, настройка отчёта в профиле | следующим шагом |

Локально Mini App проверяется через HTTPS-туннель: `cloudflared tunnel --url http://localhost:8080`
(или ngrok), адрес туннеля — в `WEBAPP_URL`, затем `python -m bot.main`.

## Локальный запуск

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements-dev.txt
cp .env.example .env   # вписать BOT_TOKEN и ADMIN_IDS
python -m bot.main
```

Тесты: `pytest`

## Команды бота

| Команда | Кто | Что делает |
|---|---|---|
| `/start` | все | онбординг / продолжить с текущего шага |
| `/help` | все | список команд (админу — и админские) |
| `/checkin` | участница | чек-ин недели: ✅/❌ по тактикам → % и оценка |
| `/plan` | участница | мои приоритеты, «зачем» и тактики |
| `/newcycle` | участница | начать новый цикл после 12 недель (или после паузы) |
| `/team` | участница | моя команда и % выполнения за неделю (только проценты) |
| `/teams` | админ | все команды с telegram_id участниц |
| `/moveteam <telegram_id> <team_id\|new>` | админ | перевести участницу в другую / новую команду |
| `/report <telegram_id> [team\|admin\|none]` | админ | куда отправлять отчёт участницы (без аргумента — показать) |
| `/linkteam <team_id>` | админ, **в группе** | привязать этот групповой чат к команде |
| `/unlinkteam` / `/unlinkteam <team_id>` | админ, в группе / в личке | отвязать чат |
| `/team` в группе | все | проценты команды за неделю |
| `/backup` | админ | прислать бэкап базы прямо сейчас |
| `/resetme` | админ | сбросить свой онбординг текущего цикла, чтобы пройти заново (команда сохраняется) |

Админы задаются в `ADMIN_IDS`. Меню команд (подсказки при вводе «/») бот ставит сам при старте: участницам — их команды,
админам — ещё и админские (админ должен хотя бы раз написать боту, иначе Telegram не даст поставить ему меню —
тогда достаточно перезапустить бота). На неизвестную команду бот отвечает подсказкой, а при ошибке пишет участнице
«что-то пошло не так», а админам — суть ошибки.

Часовой пояс — `TIMEZONE`, по умолчанию `Asia/Almaty` (Астана, UTC+5 — с 1 марта 2024 весь Казахстан
живёт по этому времени). Отдельной зоны `Asia/Astana` не существует; бот принимает её как синоним `Asia/Almaty`.
Сервер Fly работает по UTC, но все даты и расписания бот считает в `TIMEZONE`: и время рассылок,
и границы недель (неделя — с понедельника 00:00 по Астане).

Общий старт цикла — `CYCLE_START` (понедельник, сейчас 2026-10-05): кто прошёл онбординг раньше, стартует
в этот день; кто позже — с ближайшего понедельника. При запуске бот переносит на общую дату тех, чей
цикл был назначен раньше и ещё не начался.

Расписание: чек-ин — `CHECKIN_DAY` в `CHECKIN_TIME` (по умолчанию воскресенье 18:00),
напоминание о старте недели с подсказкой про буфер — понедельник в `PLANNING_TIME` (09:00),
бэкап базы всем `ADMIN_IDS` — каждую ночь в `BACKUP_TIME` (03:00).

## Структура

```
bot/
  main.py          точка входа, сборка Dispatcher
  config.py        настройки из .env (BOT_TOKEN, DATABASE_PATH, ADMIN_IDS, TIMEZONE)
  db.py            движок SQLite, сессии
  migrate.py       применение миграций при старте (с копией базы перед изменениями)
  migrations/      миграции Alembic (versions/ — по файлу на изменение схемы)
  models.py        все таблицы
  middlewares.py   сессия БД на каждый апдейт
  texts.py         все тексты бота
  keyboards.py     inline-клавиатуры
  (webapp/)        FastAPI: app.py (API + статика), auth.py (initData), static/ (фронтенд)
  handlers/        group.py (чат команды: /linkteam, /unlinkteam, /team в группе),
                   start.py (/start), wheel.py (колесо баланса), cycle.py (итоги цикла, /newcycle),
                   onboarding.py (Explore, Eliminate, Intent, тактики, /plan),
                   teams.py (/team, /teams, /moveteam), checkin.py (/checkin, /report)
  scheduler.py     APScheduler: воскресный чек-ин, понедельничное напоминание, ночной бэкап
  backup_job.py    отправка бэкапа админам
  team_notify.py   сообщения всей команде: в чат, если привязан, иначе в личку
  handlers/admin.py  /backup
  services/backup.py копия через SQLite backup API, восстановление из restore.db
  services/        бизнес-логика без привязки к Telegram
tests/
```

Путь к базе задаётся `DATABASE_PATH` — на Fly.io это будет путь на persistent volume (например `/data/bot.db`).

## Групповой чат команды

1. Создайте группу в Telegram, добавьте туда бота.
2. Желательно сделайте бота **администратором** с правом «Пригласительные ссылки» (и «Блокировка участников» —
   чтобы при `/moveteam` бот убирал участницу из чата прежней команды).
3. В группе напишите `/linkteam <team_id>` (id — из `/teams` в личке с ботом).

Бот поприветствует команду в группе, создаст ссылку-приглашение и отправит её каждой участнице в личку.
Дальше в чат идут: еженедельные отчёты (только проценты), «новая участница», «перешла в другую команду».
Ссылка на чат видна участницам в `/team`.

- Без привязанного чата (или если бота удалили из группы) всё это идёт участницам в личку, как раньше;
  админам придёт предупреждение, что чат отвязан.
- Один чат — одна команда. Если группа станет супергруппой (Telegram меняет ей id), бот сам обновит привязку.
- **Приватность:** в группе работают только `/linkteam`, `/unlinkteam` и `/team`. Личные команды
  (`/checkin`, `/plan`, онбординг, админские списки) в группе игнорируются — иначе цели, тактики
  или чужие telegram id увидели бы все.

## Жизненный цикл участницы

1. Онбординг: колесо баланса → Explore → Eliminate (ровно 3) → «зачем» → тактики → команда.
2. 12 недель: понедельник — напоминание с тактиками, воскресенье — чек-ин и отчёт.
3. Понедельник 13-й недели — вместо плана приходят **итоги**: средний %, 12 недель цветными квадратами,
   сколько недель на 85%+, лучшая неделя, вопросы для размышления. 12-ю неделю ещё можно отметить через `/checkin`.
4. Выбор: **новый цикл** (снова колесо — с сравнением «было → стало», в Explore подсказка с прошлыми приоритетами,
   команда остаётся прежней) или **пауза** (ничего не приходит, вернуться — `/newcycle`).

## Изменение структуры базы (миграции)

Бот сам применяет миграции при каждом старте — локально и на Fly, отдельно запускать ничего не нужно.
Перед применением на непустой базе он кладёт копию в `backups/` рядом с базой
(`/data/backups/pre-migration_<было>-to-<стало>_<дата>.db`, хранятся 5 последних).

Как поменять схему:

```bash
# 1. Изменить модели в bot/models.py
# 2. Сгенерировать миграцию (сравнивает модели с базой из DATABASE_PATH, база должна быть на последней ревизии)
alembic revision --autogenerate -m "add timezone to users"
# 3. Открыть созданный файл в bot/migrations/versions/ и проверить: autogenerate не всё понимает
#    (например, переименование колонки он видит как «удалить + добавить» — данные пропадут)
# 4. pytest — тест test_migrations_match_models упадёт, если модели и миграции разошлись
# 5. Закоммитить модели вместе с миграцией; при деплое бот применит её сам
```

Полезное: `alembic current` — текущая ревизия базы, `alembic history` — список миграций,
`alembic check` — есть ли изменения моделей без миграции.

Важно для SQLite: большинство изменений таблиц Alembic делает пересозданием таблицы. Бот применяет
миграции с выключенными внешними ключами — иначе пересоздание, например, `users` каскадно удалило бы
все связанные строки (приоритеты, чек-ины, членство в командах). Тест это проверяет.

## Деплой на Fly.io

База — файл SQLite на **persistent volume** (`/data/bot.db`). Без volume файл жил бы в
файловой системе контейнера и пропадал при каждом деплое и перезапуске.

> Про стоимость: условия бесплатного тарифа Fly менялись — для новых аккаунтов его может не быть.
> Проверьте актуальные цены на https://fly.io/docs/about/pricing/. Боту нужна машина shared-cpu-1x
> с 512 МБ памяти (на 256 МБ его убивало «Out of memory») и volume на 1 ГБ.

Один раз:

```bash
# 1. Установить flyctl и войти: https://fly.io/docs/flyctl/install/
fly auth login

# 2. Создать приложение. Имя уникально во всём Fly — если занято, поменяйте его и в fly.toml (app = "...")
fly apps create twelve-weeks-astana

# 3. Создать volume в том же регионе, что primary_region в fly.toml
fly volumes create bot_data --size 1 --region fra --app twelve-weeks-astana

# 4. Секреты — токен и админы (в репозиторий не попадают)
fly secrets set BOT_TOKEN=123456:ABC... ADMIN_IDS=123456789 --app twelve-weeks-astana

# 5. Деплой. Ровно ОДНА машина: две одновременно опрашивали бы Telegram (ошибка Conflict)
#    и у каждой была бы своя отдельная база
fly deploy --ha=false
```

Дальше обновление — просто `fly deploy`. Полезное:

```bash
fly logs                 # логи бота
fly status               # должна быть одна машина в состоянии started
fly scale count 1        # если машин вдруг стало больше
fly ssh console          # зайти внутрь; база лежит в /data/bot.db
```

## Бэкапы и восстановление

Каждую ночь бот присылает всем `ADMIN_IDS` файл базы документом (`12wy-bot_ГГГГ-ММ-ДД_ЧЧММ.db`)
с подписью: сколько участниц, команд и отметок. Копия делается через SQLite backup API и проверяется
`integrity_check`, так что файл целостный и самодостаточный. Если бэкап не удался — админам придёт
сообщение об ошибке. Вручную — команда `/backup`.

Дополнительно Fly сам делает ежедневные снапшоты volume (`fly volumes snapshots list <volume_id>`).

Восстановить из бэкапа:

```bash
# 1. Скачать нужный файл из Telegram, затем загрузить его на volume под именем restore.db
fly ssh sftp shell --app twelve-weeks-astana
» put 12wy-bot_2026-09-27_0300.db /data/restore.db
# 2. Перезапустить бота
fly apps restart twelve-weeks-astana
```

При старте бот увидит `/data/restore.db`, проверит его и подменит им базу. Прежняя база
не удаляется — она остаётся рядом как `bot.before-restore-<дата>.db`. Если файл битый,
бот запишет ошибку в лог и продолжит работать с текущей базой.

Локально это работает так же: положите файл рядом с базой как `data/restore.db` и перезапустите.
